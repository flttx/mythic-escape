# Mythic Escape · 整体游戏架构（设计版 v0.5）

> 状态：设计提案，尚未创建下述 UE 资产。基于 UE5.8.3 官方 First Person **蓝图模板**，先验证克拉肯，再按需引入 C++；此文不是“已实现系统清单”。
> 阅读约定：开发全局功能读本文件，开发某一巨兽只读对应的 `docs/levels/xx_*.md`。章节索引见 `docs/CHAPTERS.md`。

## 1. 产品边界与整体游戏体验
- **类型**：PC、单人、第一人称、关卡制、电影化巨兽生存逃脱；以巨物尺度、危险互动、逃出生天为核心，无战斗、无击杀巨兽目标。
- **结构**：主菜单 / 巨兽档案馆（关卡选择与已解锁资料） / 独立章节 / 章节结算。首次建议依次解锁 01 克拉肯→02 利维坦→03 耶梦加得→04 贝希摩斯→05 齐兹；后续可支持选关重玩。
- **叙事**：不强设跨世界统一年代或主角身份。各章是“遭遇神话巨兽”的独立生存短篇，允许北欧、古海、深潜、山岳不同文化语境；用环境叙事、无线电/旁白（可关闭）串接“目击档案”，避免大段强制剧情。
- **玩家能做的事**：驾驶或徒步、自由观察、根据环境读懂威胁、限时选择路径、操作载具/机关、避险、回望巨兽。巨兽不是 BOSS 血条，而是具有空间存在和运动因果的灾难源。
- **可调整参数**：倒计时、危险预警、相机震动、输入连击与辅助模式、随机种子、检查点、画质档位。全案禁止依赖无法闪避的随机即死攻击。

## 2. 核心状态、双时长档及胜负契约（v0.5）
`ChapterSelect → LOAD/READY → CALM → OMEN → REVEAL → ESCAPE_PHASE_1..N → AFTERMATH → RESULT`；危险阶段可 `FAIL → RETRY_CHECKPOINT / RESTART_CHAPTER`。状态机复用，关卡内部节拍及巨兽动作不重复。
- **`ChapterLengthProfile = PrototypeSlice | FullChapter`**：早期仅克拉肯原型使用短版，正式五章使用 Full。切换模式需要成套配置关卡路线/事件密度/阶段目标/计时与检查点，而不是仅乘一个全局时钟系数。
- `REVEAL` 后在巨兽身份与核心尺度可辨、演出事件达到 `RevealComplete` 时只启动一次当前配置的主倒计时。世界级蛇不要求全身出镜。剧情强制不操作的短转场暂停计时；单人暂停菜单同步暂停游戏世界与计时，跳过演出不得送时间。
- `ExpectedPhaseDuration[]` 为目标可操作耗时，不等于各阶段强制时限；玩家可在地形可信的安全缓冲带观察巨兽和调整路线，期间仍消耗主计时。三阶段有多个 `EncounterBeat`，不要求新增全球状态数或无限循环攻击。

| 档位/关卡 | 首次完整体验 | 可操作逃生目标（秒） | 主倒计时 | 预留容错 |
|---|---|---|---|---|
| Kraken PrototypeSlice（唯一先行原型） | 约 5–7 分 | 45/60/65 = 170 | 240 秒 | 70 秒 |
| Kraken FullChapter | 14–18 分 | 160/200/180 = 540 | 720 秒 | 180 秒 |
| Leviathan FullChapter | 17–22 分 | 220/210/290 = 720 | 960 秒 | 240 秒 |
| Jormungandr FullChapter | 17–22 分 | 220/240/260 = 720 | 960 秒 | 240 秒 |
| Behemoth FullChapter | 14–18 分 | 180/200/160 = 540 | 720 秒 | 180 秒 |
| Ziz FullChapter | 16–20 分 | 180/170/280 = 630 | 840 秒 | 210 秒 |

以上全部为**设计假设**：首次完整体验包含揭示前探索、揭示、逃生和回望，不是“倒计时秒数”。阶段目标合计约占完整倒计时 75%，容错为差值。优化时需实测首通、受伤、迷路、等待与无重试路径。不得将主倒计时拉长当作内容扩展本身。
- 仅导演 `EscapeChapterDirector` 持有阶段和胜负仲裁权；安全判定依旧为 `RouteComplete && SafeVolume && NoActiveThreat && ChapterSpecific`，满足胜利与同帧 timeout 时胜利优先；不存在独立的隐藏阶段必死计时器。
- `AFTERMATH` 停止主计时和致命危险，玩家能自由回望巨大生物，结尾可跳过；玩家输入和镜头在强制演出恢复后有安全接管窗口。

### 内容扩展与节奏实现接口
1. `PhaseDefinition` 可包含顺序或分支的 `EncounterBeats[]`：`Objective`、`PlayerChoice`、`WorldResponse`、`CarryOver`、`HazardBudget`、`ObservationPocket`、`CheckpointAnchor`。它们是设计字段建议，P0 不需一次性创建复杂数据表。
2. 每次主要行动应在约 30–60 秒内带来新的可理解选择、可感知的巨兽行为、空间变化或移动目标；允许自愿观察但避免被迫长时间等待。每个高压序列后可有有限的地形保护带，世界仍在变化，倒计时继续。
3. 可选揭示前观测点/教程既能为电影感铺垫，也要给玩家后续逃生的地图知识、路线记忆或操控练习。玩家可以绕过观测点；首次探索目标 2–5 分钟不因完成可选点变成强制清单。
4. 检查点按完整状态快照保存随机种子、巨兽/地形周期、玩家模式/载具损伤、分支选择、剩余时间，长关卡可在稳定子节拍设置恢复锚点；原型/正式档、练习/整章计时成绩分开，不得拿短版成绩冒充正式关卡成绩。
5. 未来完整关卡灰盒先验证分支在实际移动速度和巨兽危险前兆下可达，再接入大量 Tripo/Blender 模型、地形和 Niagara/Chaos 特效；不一次生产五章高精资产。

### 失败公平性、路径与安全区（沿用 v0.4，并为长关卡强化）
1. 危险遵循 `Telegraph → Windup → Active → Recovery → Cooldown`；音画/辅助提示、真正受力/伤害窗口一致；预警长度根据玩家当前速度、可达掩体、载具转向能力与路口来确定。
2. `ThreatDirector` 需确保每个长阶段内出现意外分支或环境变化后仍有**从当前玩家位置可达**的路线；同时遵守同屏威胁上限、连续致命事件冷却和观测缓冲点。保证有逃路不等于一直免死。
3. 小失误优先减速/失衡/轻伤，致命前兆明确；不可操作演出后的短暂接管保护，以及小失误重新定位的物理空间，不允许以延长的持续压力掩盖不可解困境。
4. 安全不仅是坐标，仍须`RouteComplete && SafeVolume && NoActiveThreat`与章节条件：克拉肯外流海域、利维坦稳定压力层、世界蛇安全高地、贝希摩斯稳定岩室、齐兹安全着陆背风谷。
5. `SafetyTelemetry` 添加`EncounterBeatDuration`、`OptionalExplorationTime`、`ObservationPocketTime`、`BranchUsage`、`UnexpectedDeaths`，监测是否只靠距离或反复伤害凑长；定期用正常新人/熟练路线回放固定种子。

### v0.4 章节阶段因果接口补充（设计契约）
- 阶段的目标不是只执行三个孤立小游戏：每个 `Phase` 记录 `PlayerChoice`（可读且可执行）、`WorldResponse`（由巨兽姿态/动力学驱动）和 `CarryOver`（影响下一段的路线、强度或状态）。举例：利维坦注意度影响转向但不锁死巨口逃路；耶梦加得选路影响进入蛇躯拱口的方位与耗时；贝希摩斯震波后桥体状态延续至最终岩门；齐兹教学完成但不得让新手因教学步骤失败。
- **FullChapter 的分阶段连锁是场景系统，而不只是更长的计时**：原有主动选择→巨兽响应→下一段后果可通过 `EncounterBeats` 分成多次微升级，每个节拍可设置方向变化、低压观测、短行动和分支汇合。不应同一触手/飞石/声呐攻击循环四五分钟。
- **动态路径不是静态标记**：危险生成/地形变化后应对当前玩家位置、载具实际速度、转弯半径、可用安全等待点和剩余时间校验 `AtLeastOneReachablePath`。无法满足时应延迟该危险或开启保底安全线，而不是宣称画面上有个通道即安全。
- **分支必须最终可汇合**：两条可选路线具有明确时间/风险差，但都能到达下一章阶段入口；失败或检查点读档恢复选择、地形/巨兽周期和标准剩余时间。剧情高潮不能引入不可见的第二套独立强制计时器。
- 每个关卡高潮优先采用 `玩家可控动作 + 巨兽可见动作 + 环境实际响应` 三者同步；Sequencer 负责镜头/表现，不替代真正的状态、碰撞和安全判定。本节不要求立即创建额外大型 Actor/基类，P0 可在现有蓝图导演中验证最小协议。

## 3. 核心模块（建议 Blueprint-first、接口先行）
| 模块 / 可用 UE 思路 | 拥有的状态与职责 | 章间复用 | 必需验收 |
|---|---|---|---|
| ChapterSession / GameInstance | 关卡选择、已解锁章节、存档、难度、无障碍选项 | 共用 | 启动与重试不携带脏状态 |
| EscapeChapterDirector（GameMode 或专属 Actor） | 章节阶段状态机、进入/退出钩子、超时/失败/通关 | 共用接口+章数据 | 同事件不能重复转场 |
| EscapeTimer（Component） | 主倒计时、暂停来源、调试时间、可预览 UI | 共用 | 仅 Reveal 完成启动，暂停恢复一致 |
| ChapterDefinition（DataAsset / DataTable） | 章节地图、阶段顺序、时限、角色/载具、巨兽资源、分阶段参数、镜头与音效引用 | 数据驱动 | 新章不必复制整套 GameMode |
| ThreatDirector / HazardScheduler | 威胁编排、规则随机、预警窗口、上限、冷却、可复现种子 | 共用调度、各章独有威胁 | 不随机生成无解包围 |
| GiantPresence（Actor 组合） | 巨兽空间锚点、骨骼/体量参照、主动作、视距 LOD、局部特效同步 | 共用协议，独立美术 | 主体与攻击/环境有一致因果 |
| Hazard（Actor+接口） | Telegraph → Active → Recover → Cooldown；伤害/力/碰撞只在规定窗口生效 | 共用状态协议，独立行为 | 视觉前兆与判定对齐 |
| PlayerMode / PawnSwitcher | FirstPerson/Boat/Swimmer/Submersible/Longboat/Glider 等控制权切换、相机手感、输入映射 | 通用控制协定+章载具 | 不能转场失控或卡死 |
| EnvironmentResponse | 海面/浪/风/地震/雾/落石/岩块、区域危险与表现驱动 | 参数、事件共用；求解分章 | 视觉和受力来自同一状态 |
| EncounterCinematics（Sequencer 适配） | 演出触发、输入锁范围、相机回退、跳过恢复、跨阶段编排 | 共用调用协议 | 演出被跳过也可进入正确状态 |
| HUD / Accessibility / Audio | 时间、目标方向、危险方向、行动提示、相机晃动、字幕、声音和触觉提示 | 共用样式+章小部件 | 视认清晰且支持辅助 |
| Checkpoint / Telemetry / QA | 检查点快照、重试、死亡原因、随机种子、固定镜头、帧耗时 | 共用 | 相同种子重放关键危险顺序 |

**实施原则**：上述名称是职责建议，不代表立刻创造 12 个大型基类。M1 从早期就同步制作可复用的高精巨兽/船/触手代表场景与 EpisodeDirector、Timer、BoatPawn、HUD、最小交互，持续扩展到完整首章，不因电影级画质目标而过度抽象；蓝图优先，性能瓶颈明确时再移到 C++，不强制引入 GAS、Lyra 或多人框架。

### 事件与状态数据约定（v0.3）
- `ChapterDefinition`：`ChapterId`、`Map`、`RevealCompleteEvent`、`CountdownBudget`、`PhaseDefinitions[]`、`SafeRule`、`CheckpointProfiles`、`CinematicRefs`、`EvidenceCameras`。章节独有的时间曲线和动力学置于数据或专用组件。
- `PhaseDefinition`：`PhaseId`、`ExpectedDuration`（统计用、非时限）、`Objectives`、`HazardSet`、`TelegraphPolicy`、`Recoverability`、`ExitConditions`、`CheckpointPolicy`、`TimerPolicy`。
- `PhaseEvents`：`OnOmen`、`OnRevealComplete`、`OnPhaseStarted/Completed`、`OnHazardTelegraph/Active`、`OnPawnTransferComplete`、`OnSafeConditionsMet`、`OnChapterCompleted/Failed`。仅 `EscapeChapterDirector` 更新章节状态与仲裁胜负。不要让每条触手或每块石头自行控制全局游戏状态。
- `ChapterSafetyRule` 在服务端/单机唯一模拟层中根据 `RouteComplete + SafeVolume + NoActiveThreat + ContextSpecific` 计算；状态演出和 UI 只订阅结果，不能自行根据距离归零即判赢。
- **从第一章就设计可验证性**：测试跳过 Reveal、强制碎船转场、同帧安全/超时、随机封路、连击替代输入、检查点恢复和剧情跳过；新增每章只需要组合事件协议，不复制全局 GameMode。
- 以上是职责与参数建议，P0 不要求马上创建全部数据资产。现有蓝图工程中，先用少量组件验证协议，性能/复用必要时才抽成 C++。

## 4. 操作适配与输入规则
- 统一：鼠标自由观察、Esc 暂停、重试、交互提示、相机灵敏度；**切换载具不改变视角方向习惯**。
- 各载具分开调手感：木船受水流与浮力；潜艇有惯性与垂直深度；维京长船具有惯性和顺浪操舵；步行依靠移动/冲刺/掩体；滑翔依靠风向与姿态。
- 克拉肯的“快速按方向键”保留为可选增益玩法，不做无障碍障碍：设置允许持续按键并利用正确朝向、时机和速度脱险，按键频率模式经游玩测试确认后才默认启用。
- 玩家可在危险期间观察巨兽，不强制长时间锁镜头；受击震动、晃动和动态模糊可以调低/关闭。

## 5. 电影感与真实运行的分层技术
### 高精度 3D 模型与资产制作管线（V0 起执行）

**正式视觉资产硬性要求**：玩家在代表镜头与正常操作距离内能清楚看见的巨兽、触手/吸盘、木船及关键交互物必须具有充分的**真实三维结构、可信比例与近景形体细节**。仅靠放大低模、法线贴图、灯光、粒子或景深不能掩盖明显错误的剪影、扁平吸盘、粗糙的轮廓与模型穿插。远景可使用精简表示，精度按屏幕投影、观看距离和动作需求确定，不强迫所有部件始终显示最高细节。

| 资产类别 | 必须保留的高精度表现 | V0 实施范围 |
|---|---|---|
| 克拉肯主体 | 可信头部/外套膜、眼部、皮肤起伏与比例；玩家能接近的部分具有真实体积和表面结构 | **一个可复用的高质量主体/英雄剪影**，明确近中远景的细节策略，不强求一次完成全部近景区域 |
| 可互动触手 | 沿长度连续变化的截面、真实弯曲能力、吸盘实体形体与排列、变形时不塌陷/自穿 | **至少一条高精度、可骨骼变形的 Hero Tentacle** 用于 Kraken C 镜头，其他触手可暂用代理但不能以此通过最终质量门 |
| 木船与可见玩家部位 | 船壳弧度、板材厚度、船舷、关键连接结构、可破损部件；第一人称可见手臂/身体姿态真实 | 一艘具有正式外观和尺度的 Hero Boat，玩法可先用简化物理代理；只精修实际出镜的玩家部位 |
| 环境与近景物件 | 礁石、碎木、船骸等在靠近时拥有可信轮廓与表面细节；PBR 风格与海况一致 | 只建设两个代表镜头涉及的可复用资产，非关键远景可用低成本层级 |

**优先管线**（不是强制只能使用一个平台）：确定镜头距离与动作 → Tripo 生成高质量原始模型或选用许可合规的优质现有资产 → Blender 校核生物解剖/尺度、清理噪声与破面、必要时雕刻细节及重拓扑 → 保留高精源模型，制作可动画/可交互的运行时网格与高低模细节传递（适用时烘焙） → UV、PBR 材质/纹理、骨骼蒙皮和动画 → 导入 UE5.8 → 按实际游戏镜头与性能校验。Tripo 的“高面数”不自动等于正确的形体或高质量拓扑；蒙皮前尽量完成破坏性的 Remesh/网格清理。

**质量与性能并重**：静态部件按 UE5.8 真实兼容性决定是否使用 Nanite；**骨骼变形部件不得想当然套用静态 Nanite 的做法**，根据实际支持、蒙皮质量、LOD、骨骼与材质开销选择方案。近景重点保真实轮廓，细微粗糙度/毛孔等可用贴图辅助；碰撞使用独立简化形体，不让高精视觉网格承担昂贵的逐面物理。不要提前给所有巨兽规定统一三角面数、纹理分辨率或骨骼数量，依据画面证据和目标硬件的数据确定预算。

**M1 首章高精品质线的检查点**：先在 Kraken A/C 两个代表镜头检查主体、Hero Tentacle、Hero Boat 的几何、贴图、蒙皮和性能，再随着地图/玩法完善扩展到 A–E 全镜头和全部近景关键资产。短版 PrototypeSlice 是内部快测，M1 的正式出口是 14–18 分钟全章与真实视觉质量双门均达标。测试灰盒可使用低精代理，但不能将其当作电影级品质证据。具体跨章复用见 `docs/VISUAL_PIPELINE.md`。

### M1 首章开工即建立代表性高品质实时视觉基准
- **先做有代表性的真实游戏空间，不先做全关高模**：在克拉肯章节可用的局部环境中，建立风暴海洋、真实尺度且几何结构可信的 Hero Boat、一个达到镜头所需精度的克拉肯主体/远中景剪影、**至少一条高精度且可明显弯曲并编排起势/接触的 Hero Tentacle（含立体吸盘）**，以及一致的天空/雨雾/海水/木材/生物 PBR 材质与照明。这是正式视觉资产质量基准，而非用简陋几何和静态巨兽平移冒充。
- **起步先抓最有价值的两个镜头**：A「玩家木船看克拉肯现身的巨物尺度与海浪」及 C「近景触手吸盘/船体/浪涌接触」。随着 M1 全章推进补全其余 B/D/E，M1 交付必须对五镜头完整 QA；基准镜头至少有一次动作序列验证触手起势、接触、碰撞及浪涌可信。
- **视觉与交互同场验证**：代表镜头需要在真实的场景尺寸、相机控制、船速、水面和实际运行光照设置中观察，不能独立制作一个无法复用到玩法地图的静态宣传场景。技术上可为局部效果先用简化模拟，但必须维护与正式船/巨兽/水流一致的接口和比例，避免后续全部推倒。
- **实时性能从第一天测量**：记录测试硬件、分辨率、画质档位、CPU/GPU 帧耗时与尖峰、显存/内存，并把 60 FPS 作为待选定目标硬件验证的候选指标，而不是虚构已达标。水体、体积云、雨雾、巨兽骨骼、材质的性能热点按真实测量迭代。UE Cinematic 预设/离线高质电影只作为参考，不是实时验收。
- **V0 状态要求**：真实玩家游戏视角截图与短视频/帧序列、场景参数和测量报告齐全，且视觉问题经独立审查后才可标为 `PASS`；达不到目标要记 `PARTIAL/FAIL`。UE MCP 已验证 `CaptureViewport` 返回编辑器相机（即使 PIE 活跃），不能冒充真正 GameViewport；若真实取证工具尚未打通则标 `NOT_VERIFIED`、记录阻塞，并在不依赖该结论的部分继续开发，绝不捏造截图或停滞全部工作。
- **不把 V0 变成无限美术迭代**：只做 1 个可以复用的代表区域、1 条可运动触手和必要船/海况；在品质路线清晰且最严重问题可追踪时，与 V1 核心玩法交错推进。完整版多触手、美术精修、全身正式 rig、后四章资产在后续按需制作。

- **巨兽**：使用远景低成本轮廓/LOD + 中近景高精度几何与生物结构 + 独立动画/碰撞区块；不是把单一粗糙模型放大数百倍。模型来源和详细管线参见本节高精度资产条款，Tripo→Blender→UE 可优先采用，但所有进 UE 的正式资产均须核验比例、拓扑、骨骼、材质和实景表现。
- **海洋/暴风雨**：官方 Water System 作为可测试起点；大漩涡用自定义流场/表面变形，动画水面与 BoatPawn 力学一致。Niagara 负责水花、泡沫、雨雾，不等同于船只真实受力。
- **山地/空中**：World Partition/PCG 仅在规模真的要求时使用；遮蔽、流式加载、地形破坏伪装和可玩路径首先要稳定。
- **演出**：Sequencer 负责镜头/巨兽主动作，多输入阶段仍由玩法状态与相机控制协同；跳过演出时保持阶段状态一致。
- **渲染**：Lumen、Nanite 和虚拟阴影适合对应资产，不假设可以无成本应用于所有骨骼变形、水面或体积特效。必须使用实际 PIE/打包画面验证。
- **声学**：低频隆响、方向性危险预警、巨兽水下/空中声场、风与浪节奏；危险信号有字幕/视觉替代，不能只凭声音判定躲避时机。
- **性能与规格**：先记录目标 PC/GPU 与目标 60 FPS（作为候选目标而非已达成）；按各章压力镜头测量 CPU/GPU 帧时间、显存和负载。电影离线输出与实时验收分开。
- **官方 UE 模板、插件示例与独立 Demo 参考**：以 `docs/UE_REFERENCES.md` 的 **UE_5.8 本机已核验清单、V0→V3 优先级、官方入口及逐模块验证门** 为准。V0 优先复用引擎自带 Water 示例（包括 `BP_BuoyancyExample`、Water Extras 测试关卡）、Control Rig/Niagara 能力和性能工具；Valley of the Ancient 先读巨兽技术拆解，Electric Dreams/独立 Content Examples 等大型示例按需评估，不默认下载/导入。实验性插件须在隔离环境验证，不以插件文件存在冒充工程已启用或 UE 游戏运行通过。

## 6. 人物与巨兽骨骼动画管线（设计约束，按需执行）

### 原则与工具选择
- **目标驱动，不锁死软件**：项目可组合 Tripo 自动绑定与初始动作、Blender 自定义骨骼/蒙皮/动画、Mixamo **标准双足人形**动作，以及 UE5 的 Skeleton / Animation Blueprint、IK Rig/IK Retargeter、Control Rig 和 Sequencer。具体工具须依模型拓扑、可动结构、授权/可访问性、动作质量和性能选择；不把任一服务当作必需项，也不预设所有非人巨兽都能自动绑骨。
- **分工清楚**：Tripo 用于快速试验初模/可用的自动绑定；Blender 用于清理拓扑、轴心/单位、蒙皮权重、骨骼层级与独特生物动作；Mixamo 只在适配人形模型、动作来源可合法使用时选择；UE 负责游戏事件驱动的混合、重定向、程序化控制、关卡碰撞/水流联动和电影演出。Control Rig 并非替代所有离线建模/蒙皮步骤。
- **资产顺序**：确定实际目标动作与可活动部件 → 检查原始网格结构 → **优先进行会破坏绑定的重拓扑/Remesh 和网格优化** → 制作/修正绑定及权重 → 动画片段/程序化控制 → 验证导出 FBX/GLB 适配并导入 UE → 验证真实运行表现。若重拓扑发生在绑定之后，必须重新核验权重与骨骼引用。
- **导入验证**：记录尺寸/UE 厘米单位、朝向、根骨/局部轴、缩放、绑定姿态、蒙皮变形、动画采样、LOD 和近景轮廓；角色/攻击部位的实际碰撞应独立可控，不用高模每个顶点充当物理碰撞。导入成功或自动绑定成功都**不等于**动作验收通过。

### 实体与动画职责
| 实体 | 动作最低要求 | 优先选型与特殊难点 |
|---|---|---|
| 第一人称玩家 | 船上驾驶/抓握、坠落转场、入水、划水/潜泳与游泳转向；后续可按章节扩展徒步、攀爬、抓稳、滑翔 | P0 优先复用现有 UE 角色/骨骼与基础动画，需要时用人形动作重定向；相机独立保持方向连续，手臂/身体与载具接触点一致，不强求一开始制作第三人称全套动作 |
| 克拉肯主体 | 可辨认的缓慢起伏、抬头、转眼、沉没，以及与海况关联的重心运动 | 主体远景与近景细节分层，避免仅平移/放大静态模型 |
| 克拉肯触手（独立部件） | 水下游动、盘绕/卷曲、预备抬起、砸击、横扫、回收；特殊 **托举船只→砸船** | 优先评估 **Blender 自定义柔性骨骼 + UE Control Rig/动画片段混合**。Tripo 自动绑定可先做质量试验，失败即切换，不将其视为保证可用。多条触手允许分体 rig、独立动画状态与独立碰撞 |
| 利维坦 | 眼睛注视、巨颚张合、胸/尾鳍缓慢摆动和全身游动 | 可评估 Tripo 水生类别自动绑定，复杂口腔/巨眼与鳍部由 Blender/UE 修正，声呐和吸流事件同步 |
| 耶梦加得 | 大尺度蛇体缓慢盘曲、局部抬升、形成可通行拱口 | 可评估蛇形自动绑定；近景交互段独立于远景无尽体量表现，不强迫完整世界级骨链实时解算 |
| 贝希摩斯 | 沉重四足抬足/落足、转体、擦崖及稳定足接触 | 可评估四足自动绑定，再经 Blender 权重修正与 UE 足部 IK；落足必须先于可传播震波 |
| 齐兹 | 展翼、拍翼、盘旋、尾羽变化、远飞 | 可评估鸟类自动绑定；翼骨和羽片分层修正，翼影/局部风场须随实际拍翼产生 |

### 动画事件与游戏系统对齐
- **状态与事件分离**：玩家/巨兽的动画状态由章节导演或专用动作控制器协调。危险系统负责 `Telegraph → Windup → Active → Recovery`；动画 Notify/时间轴或等价事件标出**实际接触/受力窗口**，供攻击碰撞、船体推力、海水/尘土/风效和音频订阅。不能视觉触手尚未落下，判定已经命中。
- **强制剧情**：克拉肯 K4 托举、碎船和玩家进入游泳 Pawn 在同一个转场契约下同步。跳过 Sequencer 也要产生同样的船体状态、控制权、相机方向和倒计时恢复，不把剧情船毁计成失败。
- **性能**：远景主体低开销，临近玩家或参与危险判定的触手/脚掌/翼等使用局部高精动画；骨骼数量、每帧 IK、物理链和材质形变必须按实际 UE 帧耗时配置，**不得预先规定全部生物都用同一巨型骨架**。

### 交付阶段与验证门
- **M1 首章全程**：先做一条高精且弯曲可信的代表性触手/真实船只/海域，并同步推进完整 K0–K6 和 FullChapter；短版 5–7 分钟 PrototypeSlice 只是内部快测。不得让静态假动作充当正式镜头，也不必先完成全部终极高模才开始功能测试。
- **M1 动画/玩法同步**：动画起势、接触/碰撞、浪流/船体受力、落水和危险窗口在真实 PIE 中形成一致的可玩交互，验证跳过演出、重试后的动作复位和控制权；流程成为跨章动画事件协议候选。
- **视觉品质线贯穿 M1/M2**：Tripo/Blender 高精素材、绑定、蒙皮、多动画、LOD 与 UE Control Rig/AnimBP 在各章开发中持续完善，不设置“玩法做完后才允许优化画质”的阶段；按 `mythic-visual-qa` 在真实玩家 GameViewport 审查比例、重量感、近景形变及环境同步，证据用于提炼后的跨章管线。
- **必要证据**：至少保留骨骼与网格导入检查、动作片段回放、实际交互碰撞/Notify 验证、切换/重试测试、真实 PIE 视频与帧耗时。缺少运行证据应标记 `NOT_VERIFIED`。Blender 任务才按需读取项目安装的 `blender-cli` Skill；不在普通 UE 逻辑阶段加载其完整 API 资料。

| **M3 五章最终发布** | 五章整体连贯、结算/存档/失败公平性/打包 | 画质一致的质量底线、章节独立风格、动画接触帧、LOD/性能、授权审计与视觉回归 | 五章打包可运行，关键真实画面、帧耗时、通关及回归项记录并达标 |

**实现顺序而非新里程碑**：M1 内先完成可复用的 Kraken A/C 代表镜头和必要高精资产，并可用 5–7 分钟 `PrototypeSlice`（240s/170s）快速验证 K0→K6 功能；同时逐步建立正式关卡空间和长版事件。这不是另一个需要长期打磨交付的产品，也不要求先制作全图高精资产才能测玩法。待关键系统可玩后扩充其余地形/路线和 Hero 细节，直至完整首章通过。

**首章工作流沉淀**：素材来源→Tripo/Blender 网格/材质/骨骼处理→UE 导入与动画/物理/环境响应→真实玩家视口 A–E→GPU/CPU/内存性能→缺陷修复，建立可复现的参数、原始证据及最小脚本。M1 正式通过后按 `docs/VISUAL_PIPELINE.md` 评估**扩展已有 Skill 或提炼新 Skill**；首章成功只是初始验证，必须在另一章节用不同生物/环境重复验证，才称通用 Skill 通过。不会预先假称 Skill 已存在。

**双线门槛**：只实现玩法记为 `PLAYABLE_ONLY`，只有漂亮镜头记为 `VISUAL_ONLY`；未取得真正 GameViewport/打包游戏截图、动作和性能数据则标记 `NOT_VERIFIED`。任何未通过项可继续做不依赖该项的工作，但不得宣称里程碑完成。



## 9. 验收与证据契约
- **设计门**：每章都有完整可赢/可输路径、3 个独特主动玩法、阶段转场和安全规则；已标注设计值不等于实测。
- **功能门**：UE 蓝图编译、PIE 连续通关、每阶段重试、不同随机种子、跳过演出、输入切换、计时逻辑，均附对应实测。
- **视觉门（所有里程碑持续执行）**：M1 首先按 `mythic-visual-qa` 验证克拉肯 A（登场尺度）及 C（触手近景）的真实游戏图像和短动画/帧耗时，完整首章要求本章全部 A–E；M2 每一章也要通过 A–E。现有 MCP 编辑器视口不是玩家画面，取证未证实时不能标记 VISUAL_PASS。详见 `docs/VISUAL_QA.md` 与 `docs/VISUAL_PIPELINE.md`。
- **Skill 路由**：编写设计文档不启动 unreal-mcp / visual-qa；当开始 UE 编辑器资产、镜头测试时才按需读取对应 Skill。不要因有 Skill 就每轮加载全部 Toolset。
- **验收等级**：PASS / PARTIAL / FAIL / NOT_VERIFIED。没有实际运行和截图，一律 NOT_VERIFIED。
