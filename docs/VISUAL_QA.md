# Mythic Escape · 实时视觉验收基线 v0.5（Visual-First）

> 本文件是既有 `mythic-visual-qa` Skill 的项目依据，**视觉品质线贯穿 M1 首章、M2 后四章和 M3 总验收**。一开始就审查代表镜头，不等玩法完工才做画质。该 Skill 的现有能力仍需扩展并验证真实玩家视角取证；后续可复用管线设计见 [视觉品质生产线](VISUAL_PIPELINE.md)，离线电影图与编辑器诊断图不能冒充 GameViewport。

## 每章视觉品质线：先代表镜头，再五镜头全覆盖

**M1 首章早期先审查 Kraken A（第一人称木船仰望巨兽、风暴海面）与 C（触手弯曲、吸盘、船体及海面接触）两个代表视角；首章完成前必须通过 A–E 全部镜头。M2 后四章也采用“先本章 A/C、后本章 A–E”的同一检查节奏**，但各章巨兽/地形/光照完全独立。目标是可复用的真实游戏视觉流程，不要求一天完成全章高模。

| 审查对象 | 首章早期 Hero 镜头目标（随后覆盖每章） | 证据 |
|---|---|---|
| 巨物比例/构图 | 木船与巨兽尺寸真实可信，海浪、体积雾、云层和远近遮挡形成压迫感；仍可自由观察 | 玩家游戏相机 A 镜头与场景尺寸/视角记录 |
| 高精几何与材质/天气 | Hero Tentacle 含真实形体吸盘、Hero Boat 具可信船壳与板材结构、主体近景细节可读；海水/木材/皮肤 PBR 自然，暴风雨光照/雾兼顾方向可读 | A/C 玩家 GameViewport 真实原帧 + 必要时独立模型几何检查证据 |
| 动画/接触 | 至少一条触手有弯曲、预警、接触与恢复序列，触水/船受力与粒子音效同一事件 | 连续帧/短视频与游戏事件/碰撞时序 |
| 实时可玩/性能 | 代表镜头在实际场景尺寸和操控中成立；记录 CPU/GPU 帧耗时、尖峰、显存/内存、显卡、分辨率和画质档 | 真正 PIE 玩家 GameViewport 或打包游戏的可核实录屏及性能记录 |

**验收等级不得混淆**：设计方向已确定（ART_DIRECTION_DEFINED）≠编辑器截图诊断（EDITOR_DIAGNOSTIC）≠真实玩家视角取证（RUNTIME_CAPTURE_VERIFIED）≠电影级游戏视觉验收通过（VISUAL_PASS）。UE Cinematic 画质档和离线 Movie Render Queue 也不能单独证明电影级实时游戏效果，60 FPS 仅是待指定硬件测试的候选目标。

任何代表镜头只有在真实游戏画面、动作序列及所需性能数据得到独立验证并接受实际视觉审查后才能标记 PASS。现有 MCP `CaptureViewport` 即使在 PIE 活跃时仍可能是编辑器视口：不能据此声明玩家画面已验证。取证受阻则记 NOT_VERIFIED，记录阻塞并继续可独立进行的功能/资产工作。

**审查节奏**：M1 在克拉肯实际关卡中先做 A/C 代表镜头，完成 FullChapter 前必须检查 B/D/E 并做动作/海况/性能回归；M2 对四个不同巨兽重复同一 QA 流程，M3 做五章出货验收。不要因为一张漂亮的离线图阻滞内容开发，也不要因为全流程能跑而放弃实时美术质量。

## 高精度模型质量门（每章从 A/C 代表镜头开始）

**对象和标准**：正式视觉验收中的 Hero Assets 不是高面数标签，而是近景可感知的完整形体、真实几何特征、稳定 UV/PBR 材质、可信蒙皮形变及可接受的实时成本。M1 早期最少检查克拉肯主体在 A 镜头出现的尺度/结构、**一条独立可动画的高精度触手（含有立体形体的吸盘）**、一艘具有真实可见结构的木船，以及确实出镜的玩家部位；M2 对鲸、蛇、四足兽、巨鸟分别制定其近景 Hero 结构验收，不能按触手标准机械套用。

| 验证项 | 每章 Hero 近景验收关注点 | 要记录的客观证据 |
|---|---|---|
| **几何形态与细节** | 巨兽头/眼/皮肤关键形体、触手截面及吸盘厚度/排列、木船船壳弧度/船舷/板材与损坏边缘有真实结构；轮廓无明显棱角、浮片或扁平替代 | 一张接近预期最近游玩距离的真实 GameViewport 静帧；必要时另附 Blender 网格/法线/细节诊断图，后者**不能替代**游戏证据 |
| **拓扑与骨骼形变** | 触手弯曲/盘卷/抬起/砸击时无严重塌陷、撕裂、权重穿刺、自交和吸盘脱离；人物可见身体/手臂无关节破面 | 真实游戏中至少一段起势→接触→恢复的连续帧或短视频；骨骼/权重检查记录 |
| **材质与纹理** | 表面粗糙度、法线、微细节、材质交界、海水湿润感与观察距离匹配；UV 缝、纹理模糊、拉伸、明显重复和塑料质感不可作为合格近景 | 固定曝光/FOV/分辨率的 A/C 游戏原帧、必要时 PBR 贴图与 UV 检查；不能仅凭高分辨率贴图宣称模型高精 |
| **尺度与镜头** | 模型实际尺寸、远近层级和遮挡合理；近处特征不因远景 LOD 切换突然消失/跳变 | 镜头距离与基本尺寸记录、近/中/远移动序列，查看 LOD 变化 |
| **运行开销** | 高精视觉网格、骨骼/IK、材质及 LOD 在目标硬件的真实 GPU/CPU 预算内；高精碰撞采用简化物理代理 | 同镜头帧耗时、内存/显存、画质档及硬件信息；若目标硬件未确定仅记录实测，不宣称已优化完成 |

**硬门槛**：只放大低模、用法线贴图掩盖明显错误的剪影/吸盘/船体结构、整体平移静态触手、只展示离线高模截图，都**不满足正式高精 Hero Asset 验收**。无需提前给全部模型统一写死三角面数或纹理尺寸；以镜头最近距离、真实轮廓、蒙皮状态和运行指标决定。远景适当 LOD/代理有效，但近景高精镜头必须真正使用已审查资产。

任何章节若只建立真实感灯光/环境却没有通过模型结构与形变检查，应分别记录环境效果与资产质量，不能将章节视觉品质线标记 PASS。与上文既有约定相同，真实玩家 GameViewport/打包游戏的取证尚未打通时应标记 `NOT_VERIFIED`。

## 固定验证条件

### 可执行取证（新增）
- UE5.8 工程打开并在本机 8001 端口提供 Unreal MCP 服务时，从项目根目录执行：
  - `python -X utf8 .agents/skills/mythic-visual-qa/scripts/capture_ue.py --mode editor --output Artifacts/QA/kraken/editor-check.png`（编辑器截图，只能作为诊断）。
  - `python -X utf8 .agents/skills/mythic-visual-qa/scripts/capture_ue.py --mode pie --auto-pie --output Artifacts/QA/kraken/pie-check.png`（已实测可启动/停止 PIE 并保存图片，**但 CaptureViewport 返回的仍是编辑器相机画面，不能用于宣称实时游戏画质通过**）。
- 从 UE 截图工具获取 PNG 和 `.capture.json` 之后再运行 `visual_qa.py record / verify / sheet`。脚本只检验图像元数据、哈希及生成并排对照图，**不会自动判断电影感，也无法仅凭 PIE 标志证明画面属于游戏相机**。
- 本机 Blender CLI 已安装为项目专属 Skill；只在导入/检查 Tripo 模型时加载，普通截图检查不读取其庞大 API 数据库。
同一镜头保持稳定坐标、FOV、曝光、画质档位、天气阶段和可重现的攻击种子；相机角度至少包含玩家第一人称。保存对应截图、必要的动作短视频及真实 GPU/CPU 帧耗时；记录硬件配置与分辨率。不能实际采集则标为 NOT_VERIFIED。每轮不超过三个最严重问题并给出可操作的修复项。

**当前未完成项（技术事实）：** UE MCP `EditorAppToolset.CaptureViewport` 真实接口需要完整的 `captureTransform` 和 `annotations` 参数；脚本已处理。实测 PIE 激活前后所输出截图几乎相同，因此当前只能确认视口截图管线，无法将其视为玩家游戏画面。以后必须通过独立的游戏视口/功能截图途径取得证据，再进行电影级验收。此限制不可被转述为“PIE 画质已验收”。

## 每镜头共同检查
1. 真实比例：巨兽与船、人、灯塔、山峰/建筑关系；不得靠畸变 FOV 伪造体型。
2. 姿态和运动：生物骨骼/毛发/鳞甲/吸盘/翼影结构正确；快慢、重量感与环境冲击匹配。
3. 构图和操控：玩家自由看向关键恐怖画面，不能为了构图丢失必要危险提示。
4. **近景高精模型与材质**：必须分开检查真实几何轮廓、关键可见器官/吸盘/羽毛等结构、拓扑和骨骼形变，以及高质量 PBR 材质/UV/纹理；不能靠法线贴图和特效掩盖粗糙低模。光照/雾/曝光与参考一致。
5. 真实交互：落水、巨浪、地震、强风、阴影、碰撞时序一致；“看得到就能撞到”须做玩法确认。
6. 性能：每种质量档实际运行的 GPU/CPU 帧耗时、内存和尖峰。候选目标 60 FPS，最终以指定测试硬件和正式验收标准为准。
